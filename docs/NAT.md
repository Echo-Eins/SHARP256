# NAT, проброс портов и встреча двух узлов

Этот документ отвечает на один вопрос: **при каких условиях два узла в
разных сетях, у разных провайдеров, за какими угодно NAT и межсетевыми
экранами, с IPv4, IPv6 или обоими, смогут обменяться файлом — и чем это
проверено.** Он написан так, чтобы каждое утверждение можно было
воспроизвести одной командой (раздел 7), а то, чего проверить не удалось,
названо прямо (раздел 6).

Если коротко:

* Отправитель и получатель могут **разведать свой внешний адрес и порт** и
  понять, что за NAT перед ними (`sharp-probe`; что он говорит, лаборатория
  сверяет с NAT, который сама построила, — раздел 4.5), **обменяться контактными
  карточками вручную** (`shc1-…`, одна строка, её можно передать в чате) или
  просто адресами `IP:PORT` и проверить, что пакет проходит в обе стороны,
  **не отправляя ни байта файла**. Для самой передачи обмениваются тем же,
  что печатают `sharp-receiver` и `sharp-sender` (внешний адрес — свойство
  сокета, раздел 3.4).
* Реализованы все способы прохода, которые имеют смысл для UDP-протокола
  передачи файлов: разведка (STUN, RFC 5780), проброс порта (PCP, NAT-PMP,
  UPnP-IGD v1/v2, IPv6-«пинхолы»), пробивание (одновременное, по
  предсказанию портов, «парадокс дней рождения», IPv6-межсетевые экраны,
  обе семьи сразу), встреча без сервера (карточки, mDNS, DHT), ретрансляторы
  (свой `sharp-relay`, любой TURN-сервер), переход с ретранслятора на
  прямой путь, как только он откроется, и обратно на сервер, если прямой
  путь умрёт посреди передачи.
* Единственное, чего не даёт **ничто, кроме ретранслятора**, — встреча двух
  NAT, оба из которых выдают случайный внешний порт на каждое назначение
  (RFC 4787: «symmetric»). Это не недоработка, а арифметика (раздел 2).

## 1. Чем это проверено

Всё, что ниже названо «проверено», выполнено на **настоящем ядре Linux**:
сетевые пространства имён, пары veth, трансляция и фильтрация — это conntrack
и nftables, а не имитация в самой программе. Измеряемое написано не той же
рукой, что измеряющее:

| Что | Откуда взято |
|---|---|
| Виды NAT (RFC 4787: 2 × 3 свойства) | правила nftables; каждый вид сначала проверяет независимый «оракул» — скрипт, не использующий код протокола (`natlab.py oracle`) |
| UPnP-IGD, NAT-PMP, PCP | **miniupnpd 2.3.4** (независимая реализация, сборка с nftables) |
| TURN (RFC 8656, RFC 6156) | **coturn 4.6.1** |
| DHT (BEP 5) | узел на Python в сотню строк (`dht_node.py`), не делящий кода с клиентом |
| IPv6 | ядро Linux 7.0 из пакетов Ubuntu 24.04 в виртуальной машине QEMU, потому что в контейнере, где шла работа, IPv6 в ядре выключен (`scripts/natlab/vm`); и ядро машин GitHub Actions — в CI |
| Хосты за NAT | настоящие `sharp-sender` и `sharp-receiver`, передающие настоящий файл; успех — совпадение SHA-256 у отправителя и получателя |

Топология одна и та же везде:

```
      A --lan-- RA --wan-- I(ядро) --wan-- RB --lan-- B
                            |
                            S  (ретранслятор, STUN, coturn, DHT-узел)
```

`RA` и `RB` — шлюзы, каждый со своим видом NAT (или без него); между любым
из них и «интернетом» может стоять ещё один NAT — провайдерский (CGN), со
своим видом, а роутер за ним может и вовсе ничего не транслировать (как при
DS-Lite). Границы проверки — в разделе 6.

## 2. Теория: кто с кем не встречается

### 2.1. IPv4: два независимых свойства

По RFC 4787 NAT определяют два свойства (устаревшее деление RFC 3489 на
«full cone / restricted / symmetric» — смесь этих двух):

* **отображение** — зависит ли внешний порт от адреса назначения:
  *независимо* (EIM), *от адреса* (ADM), *от адреса и порта* (APDM);
* **фильтрация** — какие входящие пакеты пропускает уже открытое
  отображение: *любые* (EIF), *от адресов, которым мы писали* (ADF), *только
  от адреса:порта, которому мы писали* (APDF).

В лаборатории шесть видов (первый — «нет NAT»):

| вид | отображение | фильтрация |
|---|---|---|
| `open` | нет NAT | — |
| `full_cone` | EIM | EIF |
| `restricted` | EIM | ADF |
| `port_restricted` | EIM | APDF |
| `symmetric_seq` | APDM, порты растут по порядку | APDF |
| `symmetric_random` | APDM, порты случайные | APDF |

Отсюда всё остальное:

* если у **одной** стороны EIM, её внешний адрес — тот же для всех, и его
  можно назвать другому; вторая сторона, даже за «symmetric», достаёт его
  обычным пакетом;
* если у обеих EIM, но фильтрация строгая, обе **одновременно** шлют друг
  другу — это и есть hole punching; для этого каждая должна знать адрес
  другой (карточка, DHT, ретранслятор-знакомящий);
* если у одной стороны «symmetric_seq», её следующий порт **предсказуем**
  (`punch::plan`: окно из 48 портов вперёд и 12 назад от последнего
  виденного, шаг измеряется);
* если у одной «symmetric_random», а у другой EIM+APDF, встречу даёт
  «парадокс дней рождения»: сторона с EIM за один проход шлёт пробные
  пакеты на 2048 случайных портов, сторона с «symmetric_random» открывает
  256 сокетов; вероятность встречи выше 99,9 %;
* если отображение зависит от назначения у **обеих** сторон (`symmetric_seq`
  или `symmetric_random`, четыре пары из тридцати шести), одного сокета
  мало: обе должны угадать порт другой одновременно, то есть совпасть в двух
  местах сразу — вариантов произведение двух неизвестных. Для счётчиковых
  NAT это выполнимо лишь при точном знании обоих следующих портов и без
  постороннего трафика; для случайных не выполнимо за время передачи.
  Реализация пробует предсказание, но **на успех не рассчитывает**: эти
  четыре пары лаборатория проводит только через ретранслятор (TURN или
  `sharp-relay`). Остальное лечит IPv6 или проброс порта на любой из сторон.

Дополнительно: **CGN** (адрес отображения из `100.64.0.0/10` или адрес
роутера «внутренний») — второй NAT перед первым; определяется, сообщается
собеседнику подсказкой `cgn` и влияет на то, чего от этого пути ждать.
**Hairpinning** (RFC 4787 REQ-9: два узла за одним NAT достают друг друга по
внешнему адресу) измеряется у NAT с отображением, не зависящим от
назначения; у «symmetric» тест бессмыслен (на свой внешний адрес ушло бы уже
другое отображение) и не делается. Есть петля — двое за одним NAT
встречаются по внешним адресам; нет — для этого случая есть адрес в
локальной сети, mDNS и ретранслятор (лаборатория проверяет оба случая,
`samenat`).

### 2.2. IPv6: NAT нет, есть межсетевые экраны

IPv6 не прячет адрес: пробивать нечего, но домашний шлюз по RFC 6092
отбрасывает незваные входящие пакеты. Три вида экранов в лаборатории:
`open6` — экрана нет, проходит всё; `stateful6` — «простая безопасность»
RFC 6092 так, как её делает conntrack Linux: проходят только ответы, с того
адреса и порта, куда хост писал (фильтрация, зависящая от адреса и порта);
`restricted6` — мягче: всё с адресов, которым хост писал, с любого их порта
(зависящая от адреса). Против любого из них работает то же одновременное
«стучание», и ещё два способа: попросить шлюз открыть **пинхол** (UPnP IGD2
`AddPinhole`, PCP) — тогда достаточно, чтобы отправитель знал адрес.

### 2.3. Обе семьи сразу

Хост с IPv4 и IPv6 имеет два пути к одному собеседнику; то, что пробивает
один, ничего не говорит о другом. Ретранслятор видит регистрацию по одному
семейству, и раньше (см. `docs/PROTOCOL.md`, «Hints») собеседнику
передавался только адрес этого семейства. Теперь вместе с ним передаётся
**адрес другого семейства** (`alt`), проверенный ретранслятором (другое
семейство, ненулевой порт, адрес глобальной маршрутизации), и обе стороны
«стучатся» и туда. Когда оба IPv4-NAT «symmetric_random» — то есть по IPv4
без ретранслятора не встретиться, — IPv6 это делает возможным в девяти
сочетаниях межсетевых экранов из девяти (раздел 4.2).

## 3. Методы: что реализовано

### 3.1. Разведка

| Что | Как | Где |
|---|---|---|
| Внешний адрес и порт | STUN Binding (RFC 8489), несколько серверов | `src/nat/stun.rs` |
| Отображение и фильтрация | RFC 5780: `CHANGE-REQUEST`, `OTHER-ADDRESS`, `RESPONSE-PORT`; ответ должен прийти *оттуда, откуда просили*; фильтрация — на отдельном, новом отображении | `behaviour.rs`, `stunserver.rs` |
| Как NAT нумерует порты | последовательно (шаг измеряется), случайно, с сохранением | `behaviour.rs` |
| Hairpinning, CGN, двойной NAT | RFC 5780 §4.5; `100.64.0.0/10`; «внешний» адрес роутера внутренний | `behaviour.rs`, `mod.rs` |
| Срок жизни отображения | RFC 5780 §4.6, `RESPONSE-PORT`: 15/30/60/120 с | `keepalive.rs` |
| Никто не ответил | тесты повторяются через 5 с, потом вдвое реже, до раза в 5 минут, пока кто-нибудь не ответит (у получателя и всего, что живёт дольше одной передачи) | `mod.rs` |
| Фильтрация IPv6 | те же тесты по IPv6 | `behaviour.rs` |
| Всё вместе, для человека | `sharp-probe`: адреса, вид NAT, карточка, проверка пробива с картой собеседника | `src/bin/probe.rs` |

Сервер без второго адреса даёт «неизвестно», а не догадку. В `sharp-relay
--stun` есть STUN-сервер с RFC 5780 для лаборатории и для тех, у кого нет
другого.

Фильтрацию меряют с **нового сокета**, который к тому времени писал только
основному адресу сервера. Тесты отображения шлют со своего сокета на второй
адрес сервера, а NAT, фильтрующий по адресу, с этой минуты его пускает:
замеренная на том же сокете, его фильтрация выглядела бы как «пускает
всех». Так и было, пока лаборатория не стала сверять сказанное с настоящим
NAT (раздел 6.4).

### 3.2. Проброс портов

| Протокол | IPv4 | IPv6 |
|---|---|---|
| PCP (RFC 6887) | `MAP`, один датаграммой всем шлюзам-кандидатам и по адресу anycast `192.0.0.9` | `MAP` открывает пинхол для этого хоста; шлюз находится по маршруту по умолчанию (`/proc/net/ipv6_route`, `route get`, `route print`), и тоже anycast: `2001:1::1` |
| NAT-PMP (RFC 6886) | да (только шлюз: anycast у протокола нет) | не существует в протоколе |
| UPnP-IGD v1 / v2 | `AddPortMapping`; порт занят — `AddAnyPortMapping` (IGD2) или несколько своих портов наугад (IGD1) | IGD2 `WANIPv6FirewallControl`: `AddPinhole`, `UpdatePinhole`, `DeletePinhole` |

Просят внешний порт, равный своему. Если он занят кем-то другим, серверы PCP
и NAT-PMP дают другой сами, и публикуется выданный (проверено `portmap
--taken`).

**PCP провайдера.** Адрес anycast PCP (RFC 7723: `192.0.0.9`, `2001:1::1`)
ведёт к ближайшему серверу PCP на пути наружу, кто бы его ни держал. Это
способ получить проброс у провайдерского NAT: RFC 6888 (REQ-9) требует от CGN
дать абоненту управлять отображениями и называет для этого PCP, а при DS-Lite
(RFC 6333) домашний роутер вообще ничего не транслирует — транслирует AFTR
провайдера, и шлюз по умолчанию о пробросе спросить бесполезно. Сервер
проверяет, что адрес в запросе совпадает с адресом отправителя: если между
хостом и CGN есть ещё один NAT (обычный домашний роутер), CGN ответит
`ADDRESS_MISMATCH`, и проброс возможен только через роутер, который сам
умеет быть посредником PCP (RFC 7648). В сети без такого сервера запрос
уходит по маршруту по умолчанию и остаётся без ответа — три датаграммы, как
неверная догадка о шлюзе. Проверено `portmap --anycast` (IPv4: роутер без
трансляции, CGN с miniupnpd, слушающим только `192.0.0.9`) и `portmap6`
(`pcp-anycast`: PCP на роутере доступен только по `2001:1::1`).

UPnP по природе не аутентифицирован: клиент верит только устройству своей
подсети и только о нём самом, у каждого шага срок, размеры ответов
ограничены (`docs/THREAT_MODEL.md`, Н4а). Аренда продлевается на половине
срока и возвращается при выходе.

Пинхол по UPnP просится **по IPv6**: поиск идёт в группы `ff02::c` и
`ff05::c` по каждой сети, где у хоста есть IPv6, а запрос `AddPinhole` уходит
с того адреса, для которого просится дыра. Так требует сам роутер: miniupnpd
(как и всё, что следует рекомендации IGD v2) открывает дыру только для
адреса самого просящего и судит об этом по адресу отправителя запроса; запрос
по IPv4 у него всегда «606, не авторизовано». Это нашла сама лаборатория: пока
PCP, другой путь к тому же результату, не был выключен на роутере, UPnP
казался рабочим, хотя дыру открывал PCP. Поиск по IPv4 остаётся вторым:
роутеры, отвечающие только по нему, тоже опрашиваются.

### 3.3. Пробивание

Одновременное открытие, «обратное» обучение адресу по чужому пакету
(*peer-reflexive*), предсказание портов, «дни рождения», IPv6-межсетевые
экраны, обе семьи сразу — всё по плану `punch::plan`, который выбирает
объём отправки по подсказкам обеих сторон (`NatHints`, 6 байт: отображение,
фильтрация, нумерация, шаг, hairpin, CGN). Подсказки — **совет, а не
власть**: собеседник может врать; худшее, что он добьётся, — несколько
девятибайтных пакетов не туда (раздел 5).

Если подсказок нет (адрес получен из DHT, введён руками или взят из имени),
пробивание идёт не одним «лёгким» способом, а по проходам: сначала как в
лёгком случае, затем так, как понадобилось бы собеседнику каждого более
жёсткого вида (строгий EIM, счётчиковый, случайный). Это добавляет несколько
секунд и спасает пары, которые без подсказок иначе не сходились.

Пробивание ради встречи (по карточке, по введённому адресу, по адресу из DHT)
длится, пока человек на той стороне может передавать строку (до пяти минут),
и **прекращается, как только сессия с этим собеседником идёт напрямую**: у
отправителя — когда его сессия не на ретрансляторе и не на TURN; у
получателя — когда сессия с этим отправителем идёт прямо и отправитель
показал, что получает на своём адресе: пакет сессии пришёл с того адреса,
откуда пришло рукопожатие (ключи сессии получаются только из ответа,
отправленного туда, а само рукопожатие ничего не доказывает — его копию могли
прислать с подделанным адресом), или адрес прошёл проверку `PATH_CHALLENGE`.
Сессия, которую несёт сервер, пробивания не останавливает: так и открывается
прямой путь (3.6).

Сокеты «дней рождения» берутся из общего на процесс запаса: половина того,
что система позволяет процессу открыть (на Linux по умолчанию 1024, на macOS
256), но не больше, чем на две встречи сразу (512). Встреча, которой
досталось меньше, открывает меньше и встречается с меньшей вероятностью;
процесс же не остаётся без дескрипторов для файла, который принимает.

### 3.4. Встреча без сервера

Внешний адрес и порт — свойство **сокета**: NAT выдаёт отображение тому
сокету, который шлёт. Поэтому стороны обмениваются адресами тех процессов,
которые будут передавать: `sharp-receiver` и `sharp-sender` выясняют свои
сами и печатают их; у `sharp-probe` сокеты свои, и его адреса годятся для его
же проверки (порядок действий — раздел 7.1).

* **Контактная карточка** (`shc1-…`): версия, роль, ID, кандидаты (хост,
  видимый снаружи, проброшенный, ретранслятор TURN), подсказки по каждому
  семейству, ретрансляторы; base32 и 4 байта контрольной суммы BLAKE3, так что
  опечатка при переписывании ловится. Получатель печатает свою при запуске,
  отправитель — получив карточку получателя; получатель принимает карточку
  отправителя, вставленную в работающий процесс, или `--peer-card`.
* **Просто адрес.** Когда карточка — лишнее, достаточно строки `IP:PORT`
  (IPv6 в скобках). Получатель печатает `Senders use: ID@адрес,адрес,…` —
  сначала адреса, видимые снаружи; за NAT, меняющим порт с назначением, в
  конце строки стоит и адрес, под которым его видел STUN-сервер: по нему
  отправитель узнаёт, откуда придёт «стук» получателя (отвечают только на
  «стук» с адреса, который есть причина пробовать). `sharp-sender --card` и
  `sharp-probe` печатают строку `Addresses:` — внешние адреса своего сокета
  (без `--card` отправитель, которому дали адрес получателя, о себе молчит:
  разведку он запускает, только когда есть кому её результат отдать).
  `sharp-receiver --peer-addr IP:PORT` (или строка, вставленная в работающий
  приёмник; можно несколько через пробел или запятую) и `sharp-probe
  --peer-addr` начинают «стучаться» туда сразу, как по карточке; отправитель
  с `--card` «стучится» по адресам, которые ввели ему. Про NAT перед
  введённым адресом ничего не известно, поэтому пробивание идёт по проходам
  (3.3). Адреса на TURN-сервере в эти строки не попадают: записанный просто
  как `IP:PORT`, он неотличим от адреса хоста, и собеседник «стучался» бы в
  чужой сервер по угаданным портам. Такой адрес передаёт только карточка, где
  сказано, что это он.
* **mDNS** (`--announce-lan` / `--lan`): в локальной сети получатель
  отвечает на одноразовый вопрос об имени, выведенном из ID; ответ принимается
  только от адреса того же канала. Выключено по умолчанию: объявление
  сообщает всей сети, что этот хост принимает SHARP-256.
* **DHT** (`--dht`): Mainline DHT (BEP 5), read-only (BEP 43); получатель и
  отправитель объявляются и ищут друг друга под инфохэшами, выведенными из
  ID получателя и общего секрета. **Цена приватности названа прямо**: каждый
  опрошенный узел узнаёт адрес хоста, а без `--secret` любой, знающий ID
  получателя, находит его адрес — так же, как если бы адрес был опубликован.
  Ничего не говорит о NAT: подсказок нет, пробивание идёт по проходам
  (см. 3.3).

### 3.5. Ретрансляторы

* **`sharp-relay`** (свой): знакомит стороны, каждой сообщает адрес другой и,
  при необходимости, **адрес другого семейства**, потом выделяет порт и
  копирует запечатанные датаграммы. Ему не доверены данные, только
  метаданные (`docs/THREAT_MODEL.md`, Н4б).
* **TURN** (`--turn USER:PASSWORD@HOST[:PORT]`, любой сервер RFC 8656): выдаёт
  адрес на сервере, который достаёт хозяина за любым NAT. Аллокация — на
  отдельном сокете; для каждого собеседника — loopback-сокет («шим»), так что
  движок передачи по-прежнему говорит на обычном UDP. Долгосрочные
  учётные данные, устаревший nonce, разрешения, привязка каналов, обновление и
  возврат аллокации. Только UDP: TURN поверх TCP/TLS — носитель, а не приём
  прохода через NAT. Пароль лучше передавать через `SHARP256_TURN`, а не
  в командной строке.
  Сервер пропускает лишь то, что от разрешённых адресов, поэтому получатель
  должен знать адрес отправителя заранее — из его карточки или из
  представления ретранслятора.
* **Пул**: сколько угодно `--relay` и `--turn`; их опрашивают одновременно, и
  выигрывает тот, кто ответил первым.

### 3.6. Переход на прямой путь

Ретранслятор — ступень, а не пункт назначения. Пока сессия идёт через
ретранслятор (порт `sharp-relay` или адрес TURN), отправитель каждую секунду
(потом раз в четыре) спрашивает остальные адреса получателя
аутентифицированным ping'ом, а чужие «стучащиеся» пакеты продолжают
учиться как адреса. Ответ вызывает обычную проверку адреса (QUIC-подобный
`PATH_CHALLENGE`), после чего сессия переезжает на прямой путь. Без этого
ответивший первым путь оставался бы путём навсегда, и ретранслятор нёс бы
то, что стороны могли бы передать сами.

Обратно на адрес сервера (порт ретранслятора, адрес TURN, TURN-шим) сторона
не уходит, пока её прямой путь слышен — последние три секунды
(`DIRECT_GRACE`). То, что приходит через сервер в это время, — другая сторона
догоняет: пакеты, отправленные до её переезда, ответы на проверки тех
секунд. Без этого правила стороны качались между путями, каждая следуя за
другой, и сессия могла закончиться на TURN при открытом прямом пути (это
нашла лаборатория, раздел 6.4).

Встреча «днём рождения» даёт отдельный сокет: сквозь NAT получателя проходит
только то, что отправлено из него. Отправитель держит этот сокет рядом с тем,
на котором начал, и читает оба. К адресу встречи пакеты уходят из сокета
встречи, ко всему остальному — прежде всего к ретранслятору и TURN — из
первого: по нему отправителя знают серверы (`sharp-relay` — по адресу, под
которым его видит; TURN-шим подключён именно к нему).

**Смена сети.** Сессия уходит с прямого пути на сервер и тогда, когда одна
из сторон сменила сеть (Wi-Fi → LTE): её пакеты выходят через другой NAT,
которому NAT другой стороны ничего не отправлял. Поэтому отправитель при
таком откате заново проверяет свой NAT (только STUN) и заново спрашивает
ретрансляторы о получателе — тем же токеном, оттуда, где он теперь.
Ретранслятор отвечает, где получатель зарегистрирован сейчас (переехавший
получатель регистрирует новое отображение при следующем keepalive), и снова
знакомит отправителя с получателем — по новому адресу и с новыми
подсказками; обе стороны бьют навстречу. Результаты — раздел 4.5.

**Обратно на сервер.** Прямой путь может умереть посреди передачи:
перезагрузился шлюз и забыл отображения, поменялось правило экрана, пропал
маршрут. Отправитель замечает тишину через 20 с (`stall_timeout`) и начинает
повторные рукопожатия по всем адресам получателя, серверным тоже, — каждое из
того сокета, откуда этот адрес достижим; кто ответил, тот и несёт сессию, и
передача продолжается с места остановки. Сервер держит путь столько, сколько
решит сам: `sharp-relay` освобождает порт пары через минуту без трафика
(`--idle`), поэтому прямой путь, умерший позже, может вернуться только на TURN
(аллокации обе стороны держат, пока работают) — или никуда, и тогда передача
останавливается через `give_up_timeout` (5 минут) с сохранённым состоянием для
продолжения. Проверено сценарием `natlab.py fallback` (раздел 4): прямой путь
перерезается посреди передачи, сервер остаётся доступен.

### 4.3. Проброс портов

**IPv4** (`portmap`): получатель — за `port_restricted` и за
`symmetric_random` — просит у miniupnpd проброс порта по PCP, NAT-PMP и
UPnP-IGD; отправитель — за каждым из шести видов NAT. 36 передач из 36 пришли на проброшенный порт роутера (`11.2.0.1:5555`): по PCP 12 из 12, по NAT-PMP 12 из 12, по UPnP 12 из 12 — в том числе от отправителей за «симметричным» NAT, которым без проброса нужен был бы сервер; правило роутера найдено для 36 из 36. Каждая
строка журнала приводит слова демона о запросе («PCP MAP: added mapping…»,
«NAT-PMP port mapping request…», «AddPortMapping: ext port…») и правило,
которое тот поставил в nftables роутера, — проброшенный порт на адрес
получателя; для строк NAT-PMP PCP на роутере отрезан, иначе проброс делал
бы PCP, который клиент спрашивает первым.

**Порт уже занят** (`portmap --taken`): прежде чем спросит получатель, порт
5555 на роутере уже проброшен кому-то другому — тем же протоколом, что
строка. Получателю достаётся порт, который выбрал роутер, и публикует он
именно его:

| Получатель просит | Передач | Получил порт | Что говорит демон | Правило роутера |
|---|---|---|---|---|
| PCP | 4 из 4 | 5556 | «PCP MAP: added mapping UDP 5556->10.2.0.2:5555» | `th dport N dnat ip to 10.2.0.2:5555` |
| NAT-PMP (PCP отрезан) | 4 из 4 | 5556 | «port 5555 protocol udp already in use» | `th dport N dnat ip to 10.2.0.2:5555` |
| UPnP, роутер IGDv2 | 4 из 4 | 5556 | «WANIPConnection:2#AddAnyPortMapping» | `th dport N dnat ip to 10.2.0.2:5555` |
| UPnP, роутер IGDv1 | 4 из 4 | 35443, 50149, 51890, 57367 | «port 5555 UDP (rhost '') already redirected to 10.2.0.99:5555» | `th dport N dnat ip to 10.2.0.2:5555` |

**PCP провайдера** (`portmap --anycast`): роутер получателя ничего не
транслирует и ничего не отвечает; NAT (`port_restricted` или
`symmetric_random`) — у провайдера, и его miniupnpd слушает только
`192.0.0.9`. 12 передач из 12 (отправитель за каждым из шести видов NAT) пришли на порт, проброшенный провайдером (`11.2.0.1:5555`); демон пишет о каждом «PCP MAP: added mapping UDP 5555->10.2.0.2:5555». Бинарники до этого изменения проброса там не получали вовсе: шлюз по умолчанию PCP не отвечает, а по `192.0.0.9` они не спрашивали.

**IPv6** (`portmap6`): экран роутера получателя не пропускает ничего
незваного; получатель просит пинхол, отправитель знает только его
IPv6-адрес и порт (ни ретранслятора, ни карточки, ни пробивания).

| Получатель просит | Результат |
|---|---|
| PCP у шлюза | отправитель вошёл через пинхол PCP MAP (`[2a0e:aa00:2:1::2]:5555`, 0,9 с) |
| PCP по `2001:1::1` (у шлюза отрезан) | отправитель вошёл через пинхол PCP MAP, запрошенный по `2001:1::1` (`[2a0e:aa00:2:1::2]:5555`, 0,9 с) |
| UPnP IGD2 `AddPinhole` (PCP отрезан) | отправитель вошёл через пинхол UPnP `AddPinhole` (`[2a0e:aa00:2:1::2]:5555`, 1,0 с) |
| ничего (контроль: демона нет) | отправитель остановлен экраном, как и должно быть (`[2a0e:aa00:2:1::2]:5555`, 25,0 с) |

### 4.4. Провайдерский NAT перед домашним роутером

`cgn`: у одной или обеих сторон между домашним роутером (`port_restricted`)
и «интернетом» стоит NAT провайдера; адрес роутера — из `100.64.0.0/10`.

| Отправитель за | Получатель за | Встреча | Результат |
|---|---|---|---|
| port + провайдер port | port | карточки | прямой путь (5,4 с) |
| port | port + провайдер port | карточки | прямой путь (5,4 с) |
| port + провайдер rand | port | карточки | прямой путь (4,4 с) |
| port | port + провайдер rand | карточки | прямой путь (5,6 с) |
| port + провайдер rand | port + провайдер rand | карточки | не соединились, как и предсказано (64,3 с) |
| port + провайдер rand | port + провайдер rand | ретранслятор | ретранслятор несёт (2,2 с) |

Два NAT подряд ведут себя как самый трудный из них: провайдер с
отображением, не зависящим от назначения, перед обычным роутером — всё ещё
обычный NAT (прямой путь); провайдер, выбирающий порт случайно для каждого
назначения, делает пару такой же, как с `rand` дома (прямой путь «днями
рождения»); два таких провайдера — пара, которой нужен сервер (4.1), и
ретранслятор её несёт.

**Обрыв прямого пути** (`fallback`): сессия, ушедшая на прямой путь, теряет
его посреди передачи (правило в «интернете» режет всё между двумя сетями,
сервер остаётся доступен):

| Отправитель | Получатель | Сервер | На прямом пути с | Снова на сервере через | Передача |
|---|---|---|---|---|---|
| port | port | ретранслятор | 4,6 с | 22,1 с после обрыва | доставлена (43,2 с) |
| rand | port | ретранслятор | 4,9 с | 20,1 с после обрыва | доставлена (41,8 с) |
| port | port | TURN | 11,0 с | 26,1 с после обрыва | доставлена (52,3 с) |
| rand | port | TURN | 10,4 с | 20,1 с после обрыва | доставлена (45,3 с) |

Двадцать секунд из них — `stall_timeout`, после которого отправитель
начинает спрашивать все адреса получателя.

**Смена сети посреди передачи** (`mobility`): у хоста есть вторая сеть со
своим роутером (как LTE у телефона в Wi-Fi); когда сессия уже идёт напрямую,
первая сеть пропадает, и маршрут уходит во вторую. Сокеты остаются теми же.
Обе сети за port-restricted NAT, если не сказано иное; 80 МБ на 16 Мбит/с:

| Кто переехал | Во что | Прямо с | Сессия догнала через | Конец |
|---|---|---|---|---|
| отправитель | port | 4,3 с | 6,0 с (получатель доказал новый адрес) | ретранслятор → прямо |
| отправитель | rand (симметричный) | 4,3 с | 6,0 с | ретранслятор → прямо |
| получатель | port | 4,3 с | 16,2 с (отправитель доказал новый адрес) | ретранслятор → прямо |
| оба | port | 4,5 с | 21,3 с | ретранслятор → прямо |

Без повторного знакомства все четыре оставались на ретрансляторе до конца:
NAT другой стороны пропускает только тех, кому та сама писала, а нового
адреса никто не знал. Без повторного теста NAT переезд в симметричный NAT
тоже оставался на ретрансляторе: подсказки описывали прежнюю сеть, и
«днём рождения» никто не бил. Время переезда получателя — до его следующего
keepalive ретранслятору (7,5–25 с, по сроку жизни отображений его NAT).

### 4.6. Ловит ли лаборатория то, ради чего написана

Таблица, в которой всё сходится, ничего не стоит, если бы она сходилась и
на сломанном коде. Поэтому часть сценариев прогнана и на коде, где нужное
выключено или ещё не исправлено; журналы — рядом с остальными.

| Что сломано или выключено | Сценарий | На коде как есть | На сломанном | Журнал |
|---|---|---|---|---|
| Предсказание портов: окно из одного названного порта | передача `seq`×`port` и `port`×`seq` по карточкам; `sharp-probe` `seq`×`port` | соединились 3 из 3 | 0 из 3 | `mutation.log` |
| «Дни рождения»: ни лишних сокетов, ни пробных залпов | передача `rand`×`port` и `port`×`rand` по карточкам; `sharp-probe` `rand`×`port` | соединились 3 из 3 | 0 из 3 | `mutation.log` |
| Разведка: фильтрация читалась на отображении, которое уже писало второму адресу сервера (6.4) | `probe --all`, отчёты хостов о своей сети | верны 72 из 72 | верны 60 из 72: все неверные — хост за `restricted`, «пускает всех» | `probe-all-before-fix.log` |
| Возврат на сервер после встречи «днём рождения» на отдельном сокете (6.4) | `fallback`, `rand`×`port` через ретранслятор | доставлена за 41,8 с, снова на ретрансляторе через 20,1 с после обрыва | не доставлена за 150,1 с | `fallback-before-fix.log` |
| PCP не спрашивался по адресу anycast | `portmap --anycast` | проброс 12 из 12 | 0 из 12 | `portmap-anycast-before-fix.log` |
| Без `DIRECT_GRACE`: сторона уходила за запоздавшими пакетами обратно на сервер | `v6 --via turn`, 60 МБ | как должно, 18 из 18 | 8 из 18 (остальные кончались на TURN) | `ipv6-turn-long-before-fix.log` |

Мутанты собраны из того же коммита с одной правкой каждый (правки приведены
в шапке `mutation.log`): предсказание — окно из одного названного порта,
«дни рождения» — ни лишних сокетов, ни пробных залпов. Больше ничего не
менялось; на тех же бинарниках без правки те же пары соединяются.

## 5. Что нельзя, и чего не делается

Просили «все возможные способы». Этот раздел — о тех, которых здесь нет, и
о причине: каждый пункт — решение, а не пропуск. Границы того, что
**реализовано, но не проверено**, — в разделе 6.

| Способ | Почему не делается | Что вместо |
|---|---|---|
| Искать и использовать **чужие открытые ретрансляторы и прокси** (публичные TURN, открытые SOCKS/HTTP-прокси, найденные сканированием) | Полоса, адрес и ответственность чужие; хозяин не согласен; найти такие серверы можно только сканируя чужие сети, а это само по себе нападение | Любые `--relay` и `--turn`, которыми вы вправе пользоваться (свои, арендованные, друзей): сколько угодно, опрашиваются одновременно |
| **Подмена адреса отправителя** (IP-spoofing) — «пробить» NAT пакетом, будто бы от чужого адреса | По BCP 38/uRPF такие пакеты режутся у провайдера; там, где нет, это уже приём атаки на третьего | Все проходы идут с настоящего адреса и своего сокета |
| **Полный перебор** 65 535 портов собеседника | Нагрузка на чужую таблицу отображений и на канал; ничего не даёт сверх «дней рождения» | Предсказание (окно из 60 портов), «дни рождения» (2048 пробных пакетов и 256 сокетов), не чаще раза в 10 с на адрес и не более восьми адресов одновременно, не дольше пяти минут и только пока сессия с собеседником не пошла напрямую (`THREAT_MODEL.md`, Н4в) |
| **Проникновение в роутер** (пароли по умолчанию, UPnP на внешнем интерфейсе, чужие устройства) | Не наше устройство | UPnP/PCP/NAT-PMP спрашивают только шлюз своей подсети (PCP — ещё и свой адрес anycast, RFC 7723) и только о себе; ответ вне подсети не слушается (Н4а) |
| **TTL-ограниченные пробные пакеты** («открыть свой NAT, не дойдя до чужого») | Нужны устройства, которым чужой ICMP-ответ ломает отображение; ни один вид NAT лаборатории таким не является, проверить нечем | Не реализовано (раздел 6) |
| **TCP hole punching** (одновременное открытие TCP), ICMP-«пробивание» | Протокол передачи — UDP; это другой носитель, а не проход для UDP | Носители — следующий этап, после этого доказательства |
| **Носители**: Tor, Snowflake, WebTunnel, CDN, туннели в ICMP и DNS | Это способ доставки, когда UDP не проходит **вовсе**, а не способ пройти NAT для UDP. Смешивать их с проходом NAT значило бы доказывать одно другим | Следующий этап: носители (UDP / TCP / TLS) и устойчивость к анализу трафика |
| **Domain fronting** | Держится на несогласии CDN; крупные CDN его закрыли, и против их условий | Не планируется |
| **Сервер PCP из DHCP** (RFC 7291) | Адрес сервера лежит в аренде DHCP, которую каждая система хранит по-своему и не всегда даёт прочесть | Шлюз по умолчанию и адрес anycast PCP (RFC 7723), куда такой сервер и ставят |
| **TURN провайдера, найденный сам** (RFC 8155: anycast `192.0.0.10`, `2001:1::2`, записи SRV) | TURN без учётных данных не выделит адрес, а стандартного анонимного доступа нет; спрашивать без них — только выдать себя | Если провайдер дал учётные данные — `--turn ЛОГИН:ПАРОЛЬ@192.0.0.10` |
| **BitTorrent-DHT как хранилище** данных или как транспорт | Каждый узел, что-то хранящий для нас, — чужой ресурс | DHT — только книга адресов: «где сейчас получатель», без единого байта файла |
| **Доверие подсказкам** собеседника о его NAT (`NatHints`) | Он может ошибаться и лгать | Подсказка — совет о том, сколько посылать; худшее, чего добьётся лжец, — потратит квоту (Н4в) |

## 6. Честные границы

Этот раздел важнее таблиц раздела 4: он говорит, где кончается то, что
доказано.

### 6.1. Где и на чём проверялось

* **IPv4** — настоящее ядро Linux (сетевые пространства имён, conntrack,
  nftables) в контейнере, где IPv6 в ядре выключен. Этот контейнер — то, на
  чём писался и проверялся код; логи — в `docs/evidence/nat/`.
* **IPv6** — ядро Ubuntu 24.04 (7.0) в виртуальной машине QEMU с
  эмуляцией процессора (TCG: медленно, но лаборатория не зависит от
  скорости) и, независимо, **ядро виртуальных машин GitHub Actions**: там
  всё то же самое запускается на каждое изменение (`.github/workflows/ci.yml`,
  задача `natlab`). Второе оказалось полезнее первого: быстрая машина
  показала гонку (отправитель приходил к ретранслятору раньше, чем получатель
  успевал зарегистрироваться), которую медленная эмуляция скрывала; она
  исправлена и закрыта тестом (`CHANGELOG.md`).
* **Независимые реализации**: miniupnpd 2.3.4, coturn 4.6.1, узел DHT на
  Python. Всё, что отвечает клиенту, написано не этим проектом.

### 6.2. Чего проверить не удалось

1. **Настоящие роутеры и операторские CGN.** Ни одного. Виды NAT лаборатории —
   модели RFC 4787 на conntrack, а не чужие прошивки. Настоящие устройства
   отличаются: сохранение порта с коллизиями, ALG, нестандартные сроки UDP,
   ограничения на число отображений, фильтрация, зависящая от интерфейса,
   собственные особенности UPnP-стеков. `sharp-probe` **измеряет** то, что
   делает ваше устройство, и подстраивается под него — но эту подстройку на
   настоящих устройствах никто не проверял. Первый настоящий прогон —
   ваш и вашего друга (раздел 7); его результат стоит прислать.
2. **Публичная сеть.** Из среды, где велась работа, наружу был открыт
   только HTTPS через прокси. Позже, 2 октября 2026 г., из одной домашней
   сети за NAT роутера проверено то, что можно проверить одной машиной
   (`docs/evidence/field/`):
   * публичные STUN-серверы по умолчанию (Google, Cloudflare) отвечают;
   * клиент Mainline DHT работает с настоящей сетью: объявление доходит до
     узлов, поиск находит его, и передача по одному ID прошла (обе стороны —
     на одной машине, через hairpinning роутера). Настоящая DHT показала
     два отличия от лаборатории, где оба узла всегда хранят объявление:
     адрес получателя назвал один узел, а не два (и без учёта ответного
     пробивания встреча не складывалась), и для нового ID узлы называли и
     согласно подтверждали чужой адрес. Оба учтены (PROTOCOL.md, «The
     DHT»). Встреча двух людей в разных сетях через DHT ещё не проверена;
   * mDNS проверен в одной сети L2; сети с изоляцией клиентов и несколько
     сегментов не проверялись.
3. **Проброс портов** проверен на одном устройстве — miniupnpd (сборка
   nftables), в том числе когда нужный порт уже занят и когда демон
   описывает себя как роутер IGDv1. Стеки производителей известны своими
   отклонениями.
4. **TURN** — только coturn, только по UDP, только с долгосрочными учётными
   данными. TURN поверх TCP/TLS/DTLS не реализован: это носитель, а не
   способ пройти NAT.
5. **macOS, BSD, Windows.** Разбор таблицы маршрутов IPv6 проверен на
   записанном выводе `route`, но лабораторию (она держится на ядре Linux)
   там запустить нельзя; обычные тесты идут в CI на всех трёх системах, а
   сборка и lint для FreeBSD — тоже.
6. **Чего лаборатория не моделирует**: ALG, NAT с ограничением скорости
   создания отображений, провайдерский NAT глубже двух уровней (проверен
   один уровень за домашним, `cgn`), сам туннель DS-Lite (его MTU и
   трансляция у провайдера — `dslite`),
   посредника PCP в роутере (RFC 7648: miniupnpd им не является),
   NAT64/DNS64 (только модульные тесты), смену IPv6-префикса, NPTv6
   (NAT66 — `nat66`, раздел 4.5).
   Потери, джиттер и узкое MTU на пути — в лаборатории плохих сетей
   (`scripts/netemlab/`, [evidence/netem](evidence/netem/)); двое абонентов
   за одним CGN — `samecgn` (раздел 4.5).
7. **Скорость.** Лаборатория проверяет, проходят ли пакеты и куда, а не
   сколько. Скорость через ретранслятор и TURN ограничена их каналом и
   квотой; таблицы ничего о ней не говорят.

### 6.3. Известные ограничения самой реализации

* **Обе стороны «symmetric»** (четыре пары из тридцати шести, только IPv4):
  без ретранслятора не встречаются. Помогают IPv6, проброс порта хотя бы на
  одной стороне, свой `sharp-relay` или TURN.
* **Возврат на сервер — пока сервер держит путь.** Сессия, чей прямой путь
  умер, возвращается на ретранслятор или TURN через 20–26 с (лаборатория,
  `fallback`), но `sharp-relay` освобождает порт пары через минуту без
  трафика: если прямой путь умрёт позже, вернуться можно только на TURN, а без
  него передача остановится через пять минут тишины, и повторный запуск
  продолжит с места остановки (состояние сохранено). После возврата на
  ретранслятор отправитель заново спрашивает его о получателе и заново
  проверяет свой NAT (раздел 3.6, «Смена сети»), так что новый прямой путь
  ищется и пробиванием; через TURN — только вопросами по известным адресам.
* **Короткая передача может закончиться на ретрансляторе**, не дождавшись
  прямого пути: сначала отвечает тот, кто быстрее, а переход происходит
  за секунды (в лаборатории — до 6 с). Поэтому ячейки «ретранслятор → прямой»
  в матрицах измерены на передачах, которые идут дольше двенадцати секунд
  (30 МБ на 20 Мбит/с): иначе результат зависел бы от скорости машины.
* **DHT и введённый руками адрес говорят только «где»**: подсказок о NAT в
  них нет, и пробивание идёт по проходам — на несколько секунд дольше, чем с
  карточкой (в лаборатории — до двадцати с небольшим секунд там, где с карточкой хватает нескольких; считая две секунды, за которые «человек» передаёт строку).
* **`sharp-probe` — снимок.** Что не ответило за его окно (до 25 с на
  тесты), то он и назовёт неизмеренным; тесты, на которые никто не ответил,
  повторяет только то, что живёт долго: получатель и отправитель, который
  печатает свою карточку или ищет получателя в DHT.
* **Адрес `sharp-probe` — не адрес передачи.** Отображение NAT принадлежит
  сокету; у проверки свой сокет, у передачи — свой. Для передачи обмениваются
  строками, которые печатают сами `sharp-receiver` и `sharp-sender` (7.1).
* **Дребезг при переходе:** пока новый путь доказывается, отправитель
  посылает по обоим; один-два пакета могут быть повторены.
* **Ретрансляторы и TURN видят метаданные** (кто с кем и сколько), не
  содержимое (`THREAT_MODEL.md`, Н4б, Н4г).
* **Не реализовано:** TTL-ограниченные пробные пакеты (раздел 5), TURN поверх
  TCP/TLS, восстановление после смены IPv6-префикса «на лету» (адрес
  публикуется заново при следующем запуске).

## 7. Как воспроизвести

### 7.1. Проверить самим, с другом, из разных сетей

Это и есть настоящий прогон — единственное, чего лаборатория заменить не
может. Ни сервер, ни ретранслятор для этого не нужны.

Внешний адрес и порт — свойство сокета (NAT выдаёт отображение тому, кто
шлёт), поэтому обмениваются адресами тех процессов, которые будут
передавать: `sharp-receiver` и `sharp-sender` выясняют их сами.

1. Получатель: `sharp-receiver --headless`. Через несколько секунд он
   печатает `Network:` (как его видно снаружи и что делает его NAT),
   `Your card: shc1-…` и `Senders use: ID@адрес,адрес,…`.
2. Любую из двух строк — другу (в чате, письмом; в карточке контрольная
   сумма, опечатка ловится).
3. Отправитель: `sharp-sender файл shc1-<карточка>` или
   `sharp-sender файл ID@адрес,… --card`. Он сразу пробует адреса получателя
   и «стучится» в них, а свои печатает: `Your card:` и `Addresses:`.
4. Эту строку — обратно; получатель вставляет её в своё окно и нажимает
   Enter. Теперь «стучатся» обе стороны; отправитель ждёт до пяти минут.
   Если `Network:` получателя говорит `reachable from outside`, шаг не
   нужен.
5. Не прошло — добавьте то, что есть под рукой: `--turn
   пользователь:пароль@сервер` обеим сторонам (пароль лучше через
   `SHARP256_TURN`) или `--relay`; сколько угодно, работает первый
   ответивший. Без обмена вообще: `--dht` (отправителю достаточно ID; цена
   приватности — в 3.4), `--announce-lan` и `--lan` в одной сети.

Проверить заранее, не передавая файла: оба — `sharp-probe` (получатель —
`sharp-probe --receiver`), обмен карточками или строками `Addresses:`
**этих `sharp-probe`**, и оба вставляют строку другого в ответ на
приглашение в те же минуты (`--wait` меняет срок, по умолчанию две минуты).
Каждый скажет, дошёл ли пакет от другого и откуда.

Карточке больше часа — программа скажет: отображения NAT живут минутами.

### 7.2. Лаборатория

Нужны Linux, `python3`, `ip`, `nft` и (для соответствующих сценариев)
`miniupnpd` со сборкой под nftables и `coturn`. Root не нужен: скрипт
запускает себя внутри `unshare -rnm`. В Ubuntu 24.04 может потребоваться
`sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0`.

```
cargo build --release --no-default-features --features nat-traversal,tls --bins
export SHARP_BIN_DIR=$PWD/target/release
python3 scripts/natlab/natlab.py oracle                   # сначала: виды NAT — те, что заявлены
python3 scripts/natlab/natlab.py matrix                   # 36 пар через ретранслятор, который несёт
python3 scripts/natlab/natlab.py matrix --direct-only     # ... который только знакомит
python3 scripts/natlab/natlab.py matrix --via card        # карточки, без сервера
python3 scripts/natlab/natlab.py matrix --via dht --timeout 60
python3 scripts/natlab/natlab.py matrix --via addr --timeout 60   # адреса, введённые руками
NATLAB_SIZE_MB=30 NATLAB_MAX_RATE=20M python3 scripts/natlab/natlab.py matrix --via turn --timeout 90
python3 scripts/natlab/natlab.py matrix --isolate         # сети не достают друг друга
python3 scripts/natlab/natlab.py portmap                  # PCP, NAT-PMP, UPnP против miniupnpd
python3 scripts/natlab/natlab.py portmap --anycast        # PCP провайдера по 192.0.0.9 (роутер не транслирует)
python3 scripts/natlab/natlab.py portmap --taken          # нужный порт уже проброшен другому: PCP, NAT-PMP, UPnP IGD2 и IGD1
python3 scripts/natlab/natlab.py cgn                      # провайдерский NAT перед домашним: два NAT подряд
python3 scripts/natlab/natlab.py lan                      # mDNS
python3 scripts/natlab/natlab.py samenat                  # двое за одним NAT, без петли и с петлёй (hairpinning)
python3 scripts/natlab/natlab.py timeout                  # NAT, забывающий отображение за секунды
python3 scripts/natlab/natlab.py early                    # отправитель раньше получателя
python3 scripts/natlab/natlab.py fallback                 # прямой путь умирает посреди передачи: назад на сервер
python3 scripts/natlab/natlab.py mobility                 # одна сторона или обе меняют сеть посреди передачи: снова напрямую
python3 scripts/natlab/natlab.py samecgn                  # двое абонентов за одним провайдерским NAT, с петлёй и без
python3 scripts/natlab/natlab.py nat66                    # NAT на IPv6: внутри уникальные локальные адреса
python3 scripts/natlab/natlab.py dslite                   # IPv4 получателя через DS-Lite: трансляция у провайдера, MTU 1460
python3 scripts/natlab/natlab.py speed --mb 100           # скорость напрямую, через ретранслятор, через TURN
python3 scripts/natlab/natlab.py probe --all --wait 12    # что говорит sharp-probe, для каждой пары, и верно ли о своём NAT
python3 scripts/natlab/natlab.py probe --all --addr --wait 45   # ... если обменялись адресами, а не карточками
python3 scripts/natlab/natlab.py pair symmetric_random port_restricted -v   # одна пара, подробно
python3 scripts/natlab/grid.py docs/evidence/nat/matrix-relay-carries.log   # таблица из журнала
```

Ядру IPv6 нужно (`v6`, `portmap6`): на машине, где оно выключено, — виртуальная
машина, `scripts/natlab/vm/README.md`; в CI это запускается прямо на машине
runner'а:

```
python3 scripts/natlab/natlab.py v6 --direct-only         # межсетевые экраны, IPv6 и обе семьи
python3 scripts/natlab/natlab.py v6 --via card|addr|dht|turn
python3 scripts/natlab/natlab.py v6 --isolate             # сети не достают друг друга
python3 scripts/natlab/natlab.py portmap6                 # PCP (и по 2001:1::1) и UPnP IGD2: пинхолы, с контролем
python3 scripts/natlab/natlab.py lan --v6                 # mDNS в сети только с IPv6
python3 scripts/natlab/natlab.py probe --v6 --wait 12     # sharp-probe по IPv6
python3 scripts/natlab/natlab.py probe --v6 --addr --wait 45   # ... если обменялись адресами
```

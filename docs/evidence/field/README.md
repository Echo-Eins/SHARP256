# Полевые проверки: журналы

Как прогонять и что присылать — [docs/FIELD.md](../../FIELD.md). Сюда
попадают только обезличенные сводки: адреса заменены метками
(`<this-network>` — внешний адрес сети, где шёл прогон; `<lan>` — домашние
адреса; `<elsewhere>` — чужие), ID — `sh-<id>`.

## 2026-10-04: из сети GitHub в домашнюю, через DHT

Отправитель — машина GitHub Actions (`.github/workflows/field.yml`,
`requests.txt`): скачивает файл по HTTPS из Википедии (`Fronalpstock_big.jpg`,
14,7 МБ) и шлёт его получателю за домашним роутером, которого ищет в
настоящей Mainline DHT по одному ID (и общему секрету). Получатель — эта
машина: `sharp-receiver --dht --secret …`.

* **Сети.** Обе — с одним внешним портом на все назначения; домашний роутер
  фильтрует входящее («впустить сначала должен сам получатель»), проброса
  портов (UPnP, NAT-PMP, PCP) не даёт; у машины GitHub — то же.
* **Итог.** Файл передан напрямую, без ретранслятора: 14,00 МиБ за 4,19 с
  (28 Мбит/с), одно событие потерь; SHA-256 совпал с тем, что скачано из
  Википедии прямо (`24eb29ec…c857`).
* **Сколько ждали.** DHT назвала отправителю адрес получателя за 10 с;
  соединение — ещё через 85 с. Отправитель объявил себя в DHT через 24 с,
  а получатель искал его раз в две минуты: за семь минут до того два узла
  DHT «согласно» назвали адрес, по которому никого не было, и получатель
  счёл отправителя найденным и стал искать реже. И первое объявление
  получателя ушло ни к одному узлу (DHT ещё не нашла узлов), а следующее —
  через пять минут. Оба исправлены (CHANGELOG): объявление, которое не взял
  ни один узел, повторяется в следующий проход, а искать реже, найдя кого-то,
  получатель больше не начинает.

Журналы прогона 1 (`dht-github-to-home-*.log`) — уровень info, адреса и
ID заменены метками.

**Прогоны 2–4.** Прогон 2, после исправления темпа: 75 с. Из них 14 с
отправитель искал получателя, прежде чем объявить себя, и раунд
получателя шёл раз в 32 с (пауза в 20 с — после поиска до 12 с). Отсюда
прогон 3: поиск и объявление разом, раунд — каждые 20 с с его начала. И
соединения не было вовсе: отправитель нашёл получателя, получатель за пять
минут не нашёл отправителя. Его объявление взяли шесть узлов, но не
ближайшие к инфохешу: клиент DHT не держал таблицы маршрутов, каждый поиск
шёл от загрузочных узлов, первый после запуска часто не доходил до
ближайших — а отправитель, объявляя разом с первым поиском, объявил по
нему. Проверка отсюда, по настоящей DHT, это подтвердила: его объявления
не находил ни один поиск, а поиски подряд находили каждый своё. Прогон 4:
клиент помнит узлы, которые ответили (до 512), и начинает поиск с
ближайших к инфохешу; поиск говорит, дошёл ли до ближайших узлов, и
объявление с недошедшего обхода повторяется в следующем раунде. 35 с до
соединения: отправитель нашёл получателя за 13 с, объявил себя на 34-й
секунде (первый обход не дошёл — объявление повторено), получатель нашёл
его через полсекунды.

Секрет и переменные репозитория, через которые прогоны получали ID
получателя, удалены после прогонов; запечатанные журналы отправителя
хранятся в артефактах прогонов три дня.

## 2026-10-02: одна машина за домашним роутером, настоящая сеть

Обе стороны на одном компьютере, за одним домашним NAT: это не прогон
между двумя сетями, а проверка того, чего не было в лаборатории, —
публичных серверов STUN и настоящей Mainline DHT.

**STUN** (`stun-home-ipv4.log`). Серверы по умолчанию — Google
(`stun.l.google.com:19302`) и Cloudflare (`stun.cloudflare.com:3478`) —
ответили. NAT роутера: один внешний порт на все назначения, hairpinning
работает; фильтрацию публичные серверы измерить не могут (у них нет
второго адреса — нужен `sharp-relay --stun` с двумя). Глобального IPv6 в
этой сети нет. Проброс порта не запрашивался (`--no-port-mapping`).

**DHT, до исправления** (`dht-real-mainline-before.log`). Объявление
получателя дошло до 8 узлов. Отправитель нашёл его адрес, но назвал его
один узел, а правило поручительства тогда требовало двух узлов — или
ответного пробивания, которое движок отправителя не учитывал: пробивания
получателя приходили с IP, о котором движок не знал, и отбрасывались. Зато
для только что созданного ID узлы DHT назвали **чужой адрес** — и
согласились в нём между собой: все 75 инициаций рукопожатия (около 100 КБ)
за пять минут ушли туда, ни одной — получателю. Узлы, которые отвечают на
`get_peers` адресами собственного изготовления, в публичной DHT есть, и
правило «два узла» их не отсеивает.

**DHT, после исправления** (`dht-real-mainline-after.log`). Адрес, который
назвал один узел, становится кандидатом, как только с его IP приходит
пробивание (получатель ищет отправителя в DHT и пробивает к нему); адрес,
который узлы назвали согласно, получает не больше 8 инициаций, пока его не
подкрепит пробивание. Передача — за 27 с с запуска отправителя, одна
инициация, файл совпал.

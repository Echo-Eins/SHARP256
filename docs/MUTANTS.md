# Мутационное тестирование

Тесты проверяются сами: cargo-mutants меняет код в одном месте за раз
(возвращает из функции `true` вместо вычисленного, меняет `<` на `<=`,
`&&` на `||`) и прогоняет тесты. Мутант, которого ни один тест не
заметил, — это недостающий тест.

## Что прогоняется

Мутируется весь крейт: библиотека, программы, GUI. После исключений это
7740 мутантов. Исключён только код, который собирают одни тесты и фаззеры:
`src/fuzz/` и то, через что harness'ы входят в модули (`DispatcherHarness`,
`RelayHarness`, `ListingBuilder`, `handshake::forge`, `fuzz_reply`,
`fuzz_answer_v6`; все они под `#[cfg(any(test, fuzzing))]`). Настройки — в
`.cargo/mutants.toml`:

* все фичи, чтобы компилировался весь код: мутант в некомпилируемом коде
  ничего не меняет и выглядел бы пропущенным;
* тесты библиотеки, программ и сквозные (`--tests`), без doctest'ов:
  каждый из них — отдельный крейт, который пришлось бы собирать заново
  для каждого мутанта;
* lint'ы не ослабляются: крейт запрещает только небезопасный код, а его
  мутации не добавляют. Ослабление поменяло бы RUSTFLAGS, и части
  пересобирали бы все зависимости вместо того, чтобы взять общий кэш.

Больше всего мутантов в отправителе (825), получателе (646), Noise (506),
описи каталога (436) и рукопожатии (299).

## Где и когда

На ноутбуке разработчика полный прогон займёт сотни часов, поэтому он идёт
в CI (`.github/workflows/mutants.yml`, cargo-mutants 27.1.0):

| Задача | Когда | Что |
|---|---|---|
| все мутанты | вручную, 9-го числа каждого месяца и при изменении настроек мутаций | сборка один раз (кэш для всех), затем 80 частей, не больше 16 одновременно; каждая с собственной базовой проверкой, что тесты проходят без мутаций; сводка всех частей |
| мутанты изменения | на каждый pull request | только мутанты в изменённых строках; если их больше 150, изменение остаётся месячному прогону |

Оценка — 1,5–2,5 минуты на мутанта на четырёхъядерном раннере: инкрементальная
сборка крейта и тестов, затем тесты (сквозные — около 25 секунд). Полный
прогон — 190–320 часов раннера, при 16 частях одновременно это 15–25 часов.
Для публичного репозитория минуты бесплатны, но всё это время прогон
занимает очередь раннеров. Число частей задаётся при ручном запуске. Если
часть не уложилась, она останавливается за 25 минут до предела задачи и
сохраняет то, что успела.

Расписание и ручной запуск GitHub берёт только с ветки по умолчанию. Первый
полный прогон запустит push коммита, который добавил этот workflow:
изменение настроек мутаций тоже его запускает.

## Как читать результат

Артефакт `mutants-summary`: `summary.md` (он же — сводка запуска) и
слитые списки `caught.txt`, `missed.txt`, `timeout.txt`, `unviable.txt`.
В артефактах `mutants-shard-N` лежат журналы каждого мутанта.

* **missed** — ни один тест не заметил. Для каждого либо пишется тест,
  который на этом мутанте падает, либо записывается, почему тест
  невозможен: мутант эквивалентен (замена ничего не меняет в поведении,
  например в журналировании или числе, которое влияет только на скорость)
  или код вне досягаемости тестов в CI (окна GUI).
* **timeout** — мутант зацикливает тесты. Это замечено, считается пойманным.
* **unviable** — мутант не собирается. Ничего не говорит о тестах.
* **В коде для других систем.** Прогон идёт на Linux x86_64 со всеми
  фичами. Мутант в коде под `#[cfg]`, который здесь ложен (Windows, macOS,
  другая архитектура, Miri, loom, сборка без фичи), ничего не меняет.
  `scripts/mutants-summary.py` вычисляет такие `cfg` над блоками, где лежит
  мутант, и выносит эти мутанты в отдельный список «not compiled here».
  Это чтение исходника, а не компилятора: список нужно просмотреть, а не
  принять на веру. На всём коде таких 121 из 7740. Мутационно их здесь
  никто не проверяет; их проверяют тесты на тех системах и clippy.

## Состояние

пять не вернули результата): 6765 мутантов, 923 не собрались; из 5842
собравшихся поймано 4031 и 143 по таймауту, пропущено 1668 — 1568 в коде,
который собирается на Linux, 100 в коде других систем. Поймано 71,4 %.
Больше всего пропущенных в `transport/sender.rs` (396), `transport/receiver.rs`
(169), `transport/congestion.rs` (108) и `nat/*`.

Раздел B5 считается сделанным, когда по каждому выжившему мутанту будет тест
или записанная причина, почему теста нет. Разобрано пока `src/crypto/` —
первым, потому что там выживало опасное.

### `src/crypto/`: 112 пропущенных в коде Linux

Хуже всего было то, что криптографию держала только совместимость обеих
сторон крейта друг с другом: nonce AEAD, заменённый нулями, константные
ключи `mac1` и cookie, другая проверка чек-суммы ID — всё это обе стороны
делали одинаково, и все тесты проходили. Теперь их ловят векторы
(`docs/vectors`, `src/crypto/vectors.rs`), которые считает вторая,
независимая реализация (`scripts/vectors`, на Go). Проверено подстановкой:
нулевой nonce роняет три теста векторов, нулевой ключ `mac1` версии 4 —
два; до этого обе мутации проходили все 66 тестов криптографии.

- `identity_file.rs` 627: сравнение двух вводов пароля с терминала.
- `secret.rs` 407: система без `mlock` (ENOSYS).

Проверка разбора — следующий полный прогон: подстановкой проверены только
самые опасные мутанты (nonce, `mac1`, страницы), остальные убиты по
рассуждению.

Локально, если машина позволяет:

```
cargo mutants --list                     # что будет мутировано
cargo mutants -f src/protocol/wire.rs    # один файл (собирает копию дерева)
cargo mutants --in-diff <(git diff main) # только изменённые строки
python3 scripts/mutants-summary.py mutants.out итог   # сводка с пометкой cfg
```

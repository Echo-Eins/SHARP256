# Модель угроз SHARP-256 (протокол версии 3)

Этот документ описывает, **от чего** SHARP-256 защищает, **от чего не
защищает** и **какой именно механизм** отвечает за каждое свойство. Он
является нормативным дополнением к `PROTOCOL.md`: спецификация говорит, как
протокол работает, модель угроз — почему он устроен именно так и где
проходит граница его гарантий.

Сила инженерного решения в области безопасности определяется не заявлением
«протокол непробиваем», а точностью формулировки того, что именно
гарантируется и при каких предположениях. Протокола, выдерживающего
произвольного противника с неограниченными возможностями, не существует:
противник, контролирующий оба конца связи, читает данные независимо от
криптографии, а противник, насыщающий канал, лишает связи любой протокол.
Поэтому ниже возможности нарушителя разделены на классы, и для каждого
класса указан достижимый результат.

Терминология: **отправитель** (sender) передаёт файл или каталог,
**получатель** (receiver) принимает. Обе стороны имеют долговременную пару
ключей X25519; публичный ключ в человекочитаемом виде — **SHARP ID**
(`sh-…`).

---

## 1. Защищаемые активы

| № | Актив | Требуемое свойство |
|---|-------|--------------------|
| A1 | Содержимое передаваемого файла или каталога | Конфиденциальность, целостность, аутентичность источника |
| A2 | Метаданные передачи: имя, размер, время изменения, структура каталога | Конфиденциальность от наблюдателя в сети |
| A3 | Долговременные закрытые ключи сторон | Секретность (вне протокола — файловые права ОС) |
| A4 | Доступность получателя: способность принимать передачи | Устойчивость к исчерпанию ресурсов |
| A5 | Файловая система получателя | Записи только в назначенный каталог, никакой перезаписи чужих данных |
| A6 | Полоса и вычислительные ресурсы обеих сторон | Невозможность использовать их как оружие против третьих лиц |
| A7 | Целостность возобновляемого состояния (resume) | Невозможность «дописать» чужие данные в частично принятый файл |

---

## 2. Предположения

Гарантии ниже верны **только** при выполнении этих условий. Каждое из них —
потенциальная точка отказа и должно проверяться при эксплуатации.

**П1. Стойкость примитивов.** X25519, ChaCha20-Poly1305, AES-256-GCM,
BLAKE2s, BLAKE3 и Argon2id стойки в общепринятом смысле. Протокол не
пытается быть стойким к противнику, умеющему взламывать эти примитивы, за
одним исключением: при заданном общем секрете (PSK) записанный трафик не
раскрывается даже при взломе X25519 (см. Г3).

**П2. Подлинность обмена идентификаторами.** SHARP ID получателя доставлен
отправителю по каналу, которому пользователи доверяют (личная встреча,
мессенджер с проверкой отпечатков, заранее согласованный список).
**Протокол не способен обнаружить подмену ID на этапе его передачи между
людьми.** Это классический корень доверия: подменённый ID означает, что
пользователь с самого начала общается с другим собеседником, и никакая
криптография внутри протокола этого не исправит.

**П3. Целостность оконечных узлов.** Операционные системы обеих сторон не
скомпрометированы: закрытые ключи, принятые файлы и оперативная память не
читаются посторонним процессом. Защита от вредоносного кода на самом
хосте — задача ОС, не протокола.

**П4. Качество источника случайности.** `OsRng` даёт криптографически
стойкую случайность (эфемерные ключи, connection id, cookie-секреты, токены
валидации пути).

**П5. Монотонность часов.** Системные часы отправителя не идут назад
существенно между сеансами. На этом основана защита от повтора рукопожатия
(строго возрастающая метка времени). Нарушение приводит к отказу в
обслуживании самому себе (получатель отвергнет инициации), но не к
компрометации.

## 3. Классы нарушителя

Классы кумулятивны по возможностям, но независимы по достижимому
результату. Для каждого указано, что он **может** сделать и что из этого
**удаётся**.

### Н1. Пассивный наблюдатель

*Возможности:* видит все датаграммы между сторонами, записывает их
неограниченно долго.

*Достигает:* факта обмена трафиком между двумя адресами, его объёма,
времени и размеров датаграмм. Ничего больше.

*Не достигает:* содержимого, имён, размеров файлов, структуры каталога,
номеров пакетов, типов сообщений, границ повторных передач. Всё это
зашифровано AEAD; тип кадра и номер пакета дополнительно скрыты защитой
заголовка (header protection, как в QUIC). Connection id случаен и меняется
при каждом рукопожатии, поэтому не служит долговременным идентификатором.

*Оговорка о прямой секретности (важно для защиты).* Полезная нагрузка
**первого** сообщения рукопожатия (Noise `IKpsk2`) — это HELLO с именем и
размером файла. Она зашифрована, но ключ выводится из `e, es`, то есть с
участием долговременного ключа получателя. Следовательно, при последующей
компрометации закрытого ключа получателя **ранее записанный трафик
рукопожатия раскрывает имя и размер файла**. Само содержимое файла этим не
затрагивается: оно передаётся на ключах, полученных после обмена
эфемерными ключами обеих сторон, и остаётся защищённым (прямая
секретность). Это известное свойство паттерна IK, принятое сознательно ради
рукопожатия за один круговой обход (1-RTT) и скрытия личности отправителя.

### Н2. Внеполосный (off-path) противник

*Возможности:* не видит трафик, но может отправлять датаграммы с любым
адресом источника (спуфинг).

*Достигает:* ничего. Он не может подделать AEAD-тег транспортного пакета, а
чтобы получить ответ на рукопожатие, нужен корректный `mac1` — ключевой
хеш, ключ которого выводится из публичного ключа получателя. Не зная SHARP
ID получателя, противник не отличим от сканера: получатель **молча
отбрасывает** такие датаграммы, и порт выглядит закрытым.

Угадывание ID невозможно: это 256-битный публичный ключ.

### Н3. Активный противник на пути (on-path, MITM)

*Возможности:* видит, задерживает, отбрасывает, дублирует, переупорядочивает
и модифицирует любые датаграммы; вставляет свои с любым адресом источника.

*Достигает:* **полного отказа в обслуживании** — он может просто отбрасывать
все пакеты. Это неустранимо и является явной не-целью (см. §6).

*Не достигает:*

- **Чтения или подмены данных.** Модификация любого байта транспортного
  пакета ломает AEAD-тег, пакет отбрасывается до того, как что-либо из его
  содержимого будет использовано. Взаимная аутентификация Noise `IKpsk2`
  исключает классический MITM: получатель аутентифицирован по своему
  статическому ключу (отправитель знает его заранее), отправитель — по
  своему.
- **Повтора рукопожатия.** Инициации несут строго возрастающую метку
  времени; `ReplayGuard` помнит последнюю метку на отправителя.
- **Повтора транспортных пакетов.** Скользящее окно номеров пакетов
  (8192 пакета) отвергает дубликаты и всё, что старше окна.
- **Перенаправления потока.** Это главная нетривиальная угроза данного
  класса: аутентичность доказывает, *кто* создал пакет, но не *откуда* он
  отправлен. Противник может скопировать подлинный пакет и переслать его с
  подставным адресом источника, чтобы сессия начала слать трафик выбранной
  им жертве — на стороне отправителя это весь файл, то есть многогигабитное
  оружие. Защита: адрес, не подтвердивший себя, считается **заявкой**.
  Сессия продолжает слать на уже подтверждённый адрес, а на новый уходит
  PATH_CHALLENGE с восемью непредсказуемыми байтами. Ответ может
  сформировать только владелец сессионных ключей, и вернуться он может
  только с того адреса, куда был послан. На неподтверждённый адрес не
  уходит ничего, кроме самого вызова, поэтому механизм не даёт и усиления
  (amplification): один маленький кадр в ответ на пакет не меньшего
  размера. Рукопожатия обрабатываются так же.
- **Понижения криптостойкости (downgrade).** Версия протокола вплетена в
  prologue рукопожатия и в метки вывода ключей; сторона другой версии не
  завершит рукопожатие. Набор шифров выбирается получателем из
  предложенного внутри уже зашифрованного и аутентифицированного сообщения,
  оба варианта (AES-256-GCM, ChaCha20-Poly1305) равностойки, поэтому
  «понижать» нечего. Биты возможностей (capabilities) подтверждаются внутри
  защищённого канала; подтверждение непредложенного бита — протокольная
  ошибка.
- **Незаметного повреждения данных.** Даже если бы повреждение прошло
  AEAD, весь поток проверяется BLAKE3-256 обеими сторонами перед
  объявлением передачи успешной (FIN / FIN_ACK).

### Н4. Противник, контролирующий разрешение имён (DNS / mDNS)

*Возможности:* подменяет или отравляет ответы DNS и mDNS, включая
широковещательное обнаружение в локальной сети.

*Достигает:* задержки. Отправитель пойдёт по указанному адресу и не сможет
завершить там рукопожатие.

*Не достигает:* перенаправления передачи. Имена трактуются как **подсказки,
а не как авторитет**: разрешение возвращает *все* адреса имени (не более 8,
с чередованием семейств адресов), попытки рукопожатия перебирают их по
очереди, и решает не DNS, а криптография — завершить рукопожатие может
только владелец закрытого ключа получателя. Поддельная запись стоит
времени, но не безопасности. Побочный полезный эффект: узел, у которого
первый адрес недостижим (типичный случай — сломанный путь IPv6), больше не
блокирует передачу.

Тот же принцип распространяется на любые будущие источники адресов
(mDNS-обнаружение, рандеву-серверы, кандидаты ICE): они поставляют
кандидатов, аутентификация выносит решение.

### Н5. Противник, исчерпывающий ресурсы (DoS/DDoS)

*Возможности:* большой объём трафика, множество подставных адресов
источника, возможно знание SHARP ID получателя.

*Достигает:* насыщения канала, если его полоса сопоставима с полосой
жертвы. Неустранимо (§6).

*Ограничено:*

| Вектор | Механизм | Стоимость для получателя |
|--------|----------|--------------------------|
| Мусор на порт | Проверка `mac1` | Один ключевой хеш, ответа нет |
| Флуд инициаций с подставных адресов | Cookie (mac2), при нагрузке свыше порога | Один MAC на датаграмму, без операций с открытым ключом |
| Флуд с одного адреса | Ограничитель скорости по адресу (20/с, всплеск 40) | Счётчик в хеш-таблице |
| Флуд новыми личностями | `ReplayGuard` с вытеснением за O(1) и ограниченной ёмкостью | Постоянная стоимость независимо от размера таблицы |
| Повтор записанных инициаций | Строго возрастающие метки времени | Сравнение |
| Много одновременных сессий | Общий лимит числа сессий **и доля на одну личность отправителя**, отказ с кодом «занято» | Ограничено конфигурацией |
| Заполнение памяти данными | Границы очереди сессии (32 МиБ), буфера записи, буфера «ранних» данных каталога (16 МиБ) | Ограничено |
| Заполнение диска | Проверка свободного места до приёма, разрежённое выделение | Ограничено |
| Брошенные сессии | Истечение времени жизни простаивающей сессии | Освобождаются |

**Об усилении (amplification).** Ответ получателя на инициацию **не
превышает** саму инициацию в любом случае, доступном противнику. Единственная
крупная часть ответа — список пропусков для возобновления, а он непуст лишь
тогда, когда получатель уже хранит часть именно этой передачи именно от
этого отправителя. Идентичность отправителя аутентифицирована Noise, значит,
добиться непустого списка может только подлинный отправитель. Cookie-ответ
(64 байта) заведомо меньше инициации (не менее 136 байт плюс полезная
нагрузка). Таким образом, коэффициент усиления не превышает единицы, и
SHARP-256 непригоден в качестве отражателя для DDoS.

### Н6. Недобросовестный участник (аутентифицированный)

Отдельный класс: противник **прошёл** аутентификацию — это либо законный
собеседник, ведущий себя злонамеренно, либо владелец скомпрометированного
ключа.

**Недобросовестный отправитель** *достигает:* предложить передачу. *Не
достигает:*

- записи вне назначенного каталога: имена файлов проходят нормализацию,
  компоненты `..`, абсолютные пути, разделители каталогов и зарезервированные
  в Windows имена отвергаются;
- перезаписи существующих данных: файлы создаются в режиме «только новый»,
  готовое дерево переносится атомарным переименованием, которое **никогда**
  не замещает существующее (при конфликте имени добавляется суффикс);
- повышения привилегий через права доступа: биты set-uid/set-gid никогда не
  выставляются, права маскируются umask;
- переполнения ресурсов каталогом: длина описи, число элементов, глубина
  вложенности и длина относительного пути ограничены, опись проверяется по
  объявленному хешу **до** создания хотя бы одного файла;
- обхода решения пользователя: политика приёма может требовать явного
  подтверждения либо ограничивать список допустимых отправителей;
- вытеснения остальных отправителей: число одновременных сессий на одну
  личность ограничено отдельно от общего лимита, поэтому занять все слоты в
  одиночку нельзя — нахождение в списке разрешённых этого не меняет.

Оставшееся — предложить пользователю принять нежелательный файл. Это
вопрос политики, а не транспорта; протокол даёт для него список разрешённых
отправителей и режим подтверждения.

**Недобросовестный получатель** *достигает:* отказаться от передачи, лгать о
своём прогрессе, замедлять отправителя. *Не достигает:* заставить
отправителя считать успешной передачу, которую тот не подтвердил своим
хешем BLAKE3 (вердикт выносит отправитель), и не может вывести отправителя
из строя ложной отчётностью: ACK, описывающий больше байт, чем есть в файле,
отбрасывается непрочитанным — иначе он навсегда «отравил» бы счётчик
актуальности и подвесил передачу.

Остаётся возможность «оптимистичного ACK» — подтверждать данные раньше их
получения, разгоняя окно перегрузки отправителя. Против собеседника,
которому файл и нужен, это самовредительство; полноценная защита требовала
бы доказательства владения принятыми байтами в каждом ACK, чего не делает
и QUIC. Отмечено как остаточный риск (§7).

### Н7. Противник, цензурирующий или классифицирующий трафик

*Возможности:* наблюдает трафик, применяет анализ размеров и тайминга,
блокирует по признакам протокола, отбрасывает UDP целиком.

*Достигает на текущей версии:* блокировки. Поток SHARP-256 отличим по
структуре датаграмм и объёмам, а полная блокировка UDP делает протокол
неработоспособным.

*Статус:* сознательно вне области версии 3. Работа над устойчивостью к
анализу трафика и блокировкам (смена несущей, выравнивание размеров и
тайминга) вынесена в отдельные этапы — см. §8.

## 4. Гарантии и отвечающие за них механизмы

| № | Гарантия | Механизм | Где в коде |
|---|----------|----------|------------|
| Г1 | Конфиденциальность содержимого и метаданных передачи от наблюдателя | AEAD (AES-256-GCM / ChaCha20-Poly1305) на каждый пакет; защита заголовка | `crypto/transport.rs` |
| Г2 | Взаимная аутентификация сторон | Noise `IKpsk2_25519_ChaChaPoly_BLAKE2s`; получатель аутентифицирован своим статическим ключом (SHARP ID), отправитель — своим | `crypto/handshake.rs` |
| Г3 | Прямая секретность данных; стойкость записанного трафика к взлому X25519 при заданном PSK | Эфемерные ключи обеих сторон; PSK, выводимый Argon2id из парольной фразы и ID получателя | `crypto/handshake.rs`, `crypto/mod.rs` |
| Г4 | Невозможность повтора рукопожатия | Строго возрастающая метка времени на отправителя, `ReplayGuard` | `crypto/handshake.rs` |
| Г5 | Невозможность повтора транспортных пакетов | Скользящее окно номеров пакетов (8192) | `crypto/replay.rs` |
| Г6 | Невидимость для сканеров | `mac1`, ключ которого выводится из публичного ключа получателя; молчание при несовпадении | `crypto/handshake.rs` |
| Г7 | Отсутствие усиления и дешёвая защита от спуфинг-флуда | Cookie (mac2), привязанный к адресу источника, с ротацией секрета каждые 120 с | `crypto/handshake.rs` |
| Г8 | Невозможность перенаправления потока на третье лицо | Валидация пути PATH_CHALLENGE / PATH_RESPONSE | `transport/path.rs` |
| Г9 | Нечувствительность к подмене DNS/mDNS | Разрешение имени во все адреса, перебор кандидатов, решение — за рукопожатием | `address.rs`, `transport/sender.rs` |
| Г10 | Побайтовая корректность результата | BLAKE3-256 всего потока, сверка обеими сторонами (FIN / FIN_ACK) | `file/mod.rs`, `transport/*` |
| Г11 | Безопасность записи на диск | Нормализация имён, «только новый», атомарное переименование без замещения, маскирование прав, проверка описи каталога по хешу до создания файлов | `file/tree.rs`, `file/mod.rs` |
| Г12 | Ограниченность потребляемых ресурсов и справедливость их распределения | Общий лимит сессий и доля на отправителя, лимиты очередей, описи каталога, буферов; истечение простаивающих сессий | `transport/receiver.rs`, `protocol/constants.rs` |
| Г13 | Устойчивость к ложным ICMP о размере пакета | Размер пакета увеличивается **только** по аутентифицированному PROBE_ACK; поддельный ICMP способен лишь уменьшить его до безопасного значения, то есть замедлить, но не нарушить | `transport/sender.rs` |
| Г14 | Ограничение срока жизни ключа AEAD | Смена ключа каждые 2²² пакетов по эпохам, без сигнализации | `crypto/transport.rs` |

## 5. Устойчивость к сетевым аномалиям

Отдельно от злого умысла: протокол обязан переживать недружелюбную, но не
управляемую противником сеть.

| Явление | Поведение |
|---------|-----------|
| Потеря пакетов (в том числе пачками) | Выборочные подтверждения, обнаружение потерь RACK (RFC 8985), зонды хвостовой потери, таймаут повторной передачи |
| Дублирование | Окно номеров пакетов отбрасывает дубликаты |
| Переупорядочивание | Порядок отправки, а не смещение в файле, определяет признание потери; окно переупорядочивания адаптивно |
| Внезапный разрыв и возврат связи | Сессия переходит в состояние «застоя», шлёт зонды живости, затем новое рукопожатие; передача продолжается с места остановки |
| Перезапуск любой из сторон | Возобновление по устойчиво сохранённому состоянию; получатель сообщает точную картину принятого |
| Смена адреса (NAT rebinding, смена сети) | Валидация пути: один круговой обход — и сессия следует за собеседником |
| Чёрная дыра по размеру пакета (MTU) | Зондирование пути, откат к безопасному размеру, обработка EMSGSIZE |
| Переполнение очереди устройства (ENOBUFS) | Обратное давление с коротким отступом |
| Отказ сегментации на уровне драйвера | Прозрачный откат на по-датаграммную отправку |
| ICMP «порт недоступен» на Windows | Поведение отключено (SIO_UDP_CONNRESET), один ушедший собеседник не мешает остальным |
| Случайные (не заторные) потери | Классификация потерь: фоновая потеря не вызывает снижения окна как при заторе |

**Об «RST-атаках».** У UDP нет аналога TCP RST: не существует пакета,
который заставил бы сторону разорвать соединение. Ближайший эквивалент —
кадр ABORT, но он передаётся **внутри** аутентифицированного канала, поэтому
сформировать его может только собеседник. Подделанные ICMP-сообщения
(«порт недоступен», «требуется фрагментация») не аутентифицированы и никогда
не принимаются как основание закрыть сессию: они в худшем случае уменьшают
размер пакета до безопасного (Г13). Таким образом, внеполосное принудительное
разрывание сессии в SHARP-256 невозможно по построению — в отличие от TCP,
где оно является известной и практически применяемой техникой.

## 6. Явные не-цели

Заявлять их прямо — часть корректной модели угроз.

**НЦ1. Анонимность.** SHARP-256 не скрывает, что два конкретных адреса
обмениваются трафиком. Это не система анонимной связи, и она не заменяет
Tor или аналогичные сети.

**НЦ2. Сокрытие факта и объёма обмена.** В версии 3 размеры и тайминг
датаграмм не выравниваются, поэтому классификация трафика по этим признакам
возможна. Отдельный этап работы (§8).

**НЦ3. Защита от насыщения канала.** Противник с сопоставимой полосой может
лишить связи любой протокол. SHARP-256 ограничивает **асимметрию затрат** и
**усиление**, но не претендует на устойчивость к грубому флуду.

**НЦ4. Защита при компрометации оконечного узла.** Скомпрометированная ОС
означает доступ к ключам и к данным; протокол здесь бессилен (П3).

**НЦ5. Защита от подмены ID при его передаче между людьми.** Корень доверия
вне протокола (П2).

**НЦ6. Защита получателя от нежелательного, но аутентичного содержимого.**
Это вопрос политики приёма, а не транспорта.

**НЦ7. Сокрытие адреса источника средствами подделки IP.** Сознательно
отвергнуто: двусторонний аутентифицированный протокол требует обратного
маршрута, а подделка адреса источника является техникой атаки, а не защиты.
Легитимный способ скрыть свой адрес от собеседника — ретрансляция через
собственный узел (планируется как TURN-подобный релей, §8).

**НЦ8. Domain fronting.** Рассмотрен и отвергнут: крупные CDN закрыли эту
возможность с 2018 года, а использование чужого доменного имени в TLS SNI
нарушает условия обслуживания провайдеров. Вместо этого планируется
камуфляж под обычный TLS **к собственному узлу**, где предъявляемое имя
принадлежит владельцу (§8).

## 8. Область дальнейшей работы

Перечислено для полноты картины и разграничения сделанного от
запланированного.

1. **Преодоление NAT.** Определение типа отображения и фильтрации по
   RFC 5780, запрос проброса порта через PCP (RFC 6887) и NAT-PMP наряду с
   UPnP-IGD, сбор кандидатов и проверки связности по ICE (RFC 8445),
   рандеву и ретрансляция в стиле TURN (RFC 8656) для случая, когда обе
   стороны за симметричными NAT. Все кандидаты остаются **подсказками**:
   решение выносит аутентификация (Г9).
2. **Смена несущей.** Автоматический переход UDP → TCP с кадрированием →
   TLS при блокировке или деградации UDP, с обнаружением блокировки и
   чёрных дыр по MTU.
3. **Устойчивость к анализу трафика.** Выравнивание размеров и тайминга,
   обёртка рукопожатия, неотличимая от случайного потока (подход obfs4),
   камуфляж под обычный TLS к собственному узлу. Закрывает Р5 и НЦ2.

## 9. Соответствие проверок модели

Каждое существенное утверждение подкреплено автоматическим тестом.

| Утверждение | Тест |
|-------------|------|
| Незнающий ID не получает ответа; мусор не принимается за инициацию | `strangers_get_no_answer`, `strangers_and_tampering_are_rejected` |
| Изменение любого байта ломает рукопожатие или транспортный пакет | `strangers_and_tampering_are_rejected`, `any_modification_is_rejected`, `tampered_packets_are_ignored` |
| Различие PSK не даёт завершить рукопожатие | `different_psk_fails_at_the_response`, `mismatched_secret_fails_cleanly` |
| Повтор инициации отвергается | `replayed_initiation_is_ignored`, `replay_guard_and_limiter` |
| Повтор и устаревание транспортных пакетов отвергаются | `rejects_duplicates_and_stale`, `matches_a_set_model` |
| Cookie доказывает адрес и бесполезен с другого адреса | `cookie_roundtrip_proves_the_address`, `cookie_challenge_under_load` |
| Подставной адрес источника не перенаправляет сессию | `a_forged_source_address_never_redirects_the_session` |
| Валидация пути: вызов, повтор, отказ от заявки | тесты модуля `transport::path` |
| Недостижимый первый адрес не срывает передачу | `an_unreachable_first_address_does_not_strand_the_transfer` |
| Неразрешённый отправитель отвергается | `unauthorized_sender_is_rejected` |
| Один отправитель не занимает все слоты сессий | `one_sender_cannot_take_every_session_slot` |
| Возобновление требует того же отправителя и того же источника | `resume_requires_the_same_sender`, `changed_source_is_not_resumed_onto_stale_data` |

| Существующий файл не перезаписывается | `existing_file_is_not_overwritten_by_default` |

# SHARP-256

**S**wift **H**ash **A**ssurance **R**ust **P**rotocol — надёжная передача файлов
по UDP с проверкой целостности BLAKE3, адаптивным управлением скоростью и
возобновлением после обрывов.

Протокол версии 2 (пакет `sharp256` 0.4). Спецификация формата и логики —
в [docs/PROTOCOL.md](docs/PROTOCOL.md), история изменений — в
[CHANGELOG.md](CHANGELOG.md).

## Что делает

- **Целостность.** Каждый пакет данных несёт абсолютное смещение в файле и
  тег целостности (усечённый keyed BLAKE3). В конце обе стороны сверяют
  BLAKE3-256 всего файла; передача считается завершённой только при
  совпадении.
- **Точность подтверждений.** Выборочные подтверждения (SACK) с компактным
  списком «дыр» (до ~300 на пакет) всегда описывают свой интервал
  *полностью*: отправитель никогда не примет недоставленный байт за
  доставленный.
- **Восстановление потерь.** RACK (RFC 8985) по порядку и времени отправки,
  хвостовые пробники (TLP), RTO с перезапуском по прогрессу и с учётом
  задержки ACK получателем. Хвост передачи восстанавливается без схлопывания
  окна.
- **Работа на нестабильных каналах.** Случайные потери (радио, плохие линии)
  отличаются от перегрузки: при фоновом уровне потерь скорость не
  снижается, при устойчивой очереди или статистически значимом росте потерь
  — снижается. В тестах передача завершается при 15 % потерь, 10 %
  перестановок и дублях.
- **Живучесть.** Обрыв связи, смена адреса, перезапуск получателя или
  отправителя, отмена по Ctrl-C — состояние сохраняется (только после
  `fsync`), передача продолжается с места остановки без повторной пересылки
  уже принятого. Изменённый с тех пор исходный файл отправляется заново.
- **Эффективность.** CUBIC с пейсингом, HyStart++ (RFC 9406) и тормозом при
  устойчивой очереди; очередь распознаётся по минимумам RTT за раунд, поэтому
  джиттер Wi-Fi и сотовых сетей не обрывает разгон. Зонд MTU пути (1432 байта
  полезной нагрузки при MTU 1500, безопасный откат к 1192); объединение
  записей на диск, упреждающее чтение, окно получателя.
- **Многосессионность.** Один получатель обслуживает до 16 одновременных
  передач (настраивается).
- **Доступность из-за NAT (опционально).** Получатель в фоне узнаёт свой
  внешний адрес через STUN и пробрасывает порт через UPnP; передачи при этом
  не ждут. Отправителю NAT не мешает.
- **Расширяемость.** Двустороннее согласование возможностей и расширяемые
  управляющие сообщения: шифрование, манифест хешей блоков, передача
  каталогов добавляются без смены версии протокола.

Чего пока **нет** (см. «Дорожная карта»): шифрования и аутентификации,
relay/rendezvous-сервера для двух сторон за NAT, передачи каталогов.

## Сборка

Требуется Rust 1.82+ (проверено на 1.82, 1.86 и 1.94; Linux и Windows).

```bash
# полная сборка (GUI + NAT); на Linux для диалогов выбора файла нужен GTK3 (libgtk-3-dev)
cargo build --release

# без GUI (серверы, контейнеры)
cargo build --release --no-default-features --features nat-traversal

# минимальная сборка (только транспорт и CLI)
cargo build --release --no-default-features
```

Бинарники: `target/release/sharp-sender` и `target/release/sharp-receiver`.

## Использование

### Получатель

```bash
sharp-receiver --headless                          # слушает 0.0.0.0:5555, пишет в ./received
sharp-receiver --headless --bind 0.0.0.0:7777 --output /data/in
sharp-receiver --headless --overwrite              # заменять одноимённые файлы вместо "name (1)"
sharp-receiver --headless --no-nat                 # без STUN/UPnP
sharp-receiver --headless --max-sessions 64 --state-dir /var/lib/sharp256
```

Получатель принимает любые корректные запросы (в GUI — с подтверждением),
складывает частичные файлы как `имя.sharp-part`, по завершении проверки
переименовывает. Ctrl-C сохраняет состояние всех активных передач. Если
собран с NAT, печатает внешний адрес, который нужно сообщить отправителю.

### Отправитель

```bash
sharp-sender /path/file.bin 203.0.113.5:5555
sharp-sender file.bin 10.0.0.2:5555 --max-rate 200M       # ограничить 200 Мбит/с
sharp-sender file.bin 10.0.0.2:5555 --chunk-size 8000     # jumbo-кадры (проверяется зондом)
sharp-sender file.bin 10.0.0.2:5555 --no-probe            # без зонда MTU
sharp-sender file.bin 10.0.0.2:5555 --log-level debug
```

Отправитель печатает прогресс: процент, скорость, RTT, окно, объём
повторных передач, оценку времени. При обрыве он ждёт получателя (по
умолчанию до 5 минут), затем выходит с сохранением состояния; повторный
запуск той же команды продолжит передачу.

### GUI

Без аргументов `sharp-sender` и `sharp-receiver` открывают окна (если собраны
с фичей `gui`). GUI управляет тем же транспортом и показывает реальный
прогресс; получатель спрашивает подтверждение на каждую входящую передачу и
показывает свою доступность из интернета.

### Библиотека

```rust
use sharp256::{Receiver, ReceiverConfig, Sender, SenderConfig, TransferEvent};
use std::sync::Arc;

async fn send() -> Result<(), sharp256::SendError> {
    let mut cfg = SenderConfig::new("10.0.0.2:5555".parse().unwrap(), "big.iso".into());
    cfg.events = Some(Arc::new(|ev: TransferEvent| {
        if let TransferEvent::Progress(s) = ev {
            println!("{:.1}% at {:.0} Mbit/s", s.fraction() * 100.0, s.rate_bps / 1e6);
        }
    }));
    let summary = Sender::new(cfg).await?.run().await?;
    println!("BLAKE3 {}", summary.file_hash_hex);
    Ok(())
}

async fn receive() -> Result<(), sharp256::RecvError> {
    let cfg = ReceiverConfig::new("0.0.0.0:5555".parse().unwrap(), "./in".into());
    let receiver = Receiver::new(cfg).await?;
    let stop = receiver.cancel_token(); // stop.cancel() завершает работу
    let _ = stop;
    receiver.run().await
}
```

`TransportConfig` (поле `transport` в обеих конфигурациях) открывает все
тайминги и лимиты: размер чанка, интервалы ACK, границы RTO, тайм-ауты
простоя и отказа, размер буферов сокета, интервал сохранения состояния.
Значения по умолчанию перечислены в разделе 8 спецификации.
`AcceptPolicy::Ask` позволяет приложению решать по каждому входящему
запросу.

## Архитектура

```
src/protocol/   константы, формат кадров (wire.rs), множество диапазонов (range_set.rs)
src/transport/  sender.rs (машина состояний отправителя), receiver.rs (диспетчер +
                сессии), congestion.rs (RTT/RTO, CUBIC, пейсер), socket.rs
src/file/       позиционное чтение, поток записи с объединением, BLAKE3 файла,
                свободное место, санитизация имён
src/state/      атомарное сохранение состояния для возобновления
src/nat/        STUN и UPnP для получателя (фича nat-traversal)
src/gui/        egui-окна (фича gui)
src/bin/        sharp-sender, sharp-receiver
tests/e2e.rs    сквозные тесты через UDP-прокси с потерями/дублями/перестановкой
```

Коротко о протоколе (подробно в `docs/PROTOCOL.md`):

1. `HELLO` → `HELLO_ACK`: имя, размер, id передачи, возможности; получатель
   отвечает тем, что у него уже есть (граница и дыры), поэтому любой повтор
   `HELLO` — это и есть возобновление.
2. `PROBE` → `PROBE_ACK`: выбор наибольшего размера пакета, который проходит
   без фрагментации.
3. `DATA` ⇄ `ACK`: данные с абсолютным смещением; подтверждения с дырами
   каждые 8 пакетов / 20 мс / при появлении пропуска.
4. `FIN` → `FIN_ACK` → `FIN_DONE`: хеш всего файла от получателя, вердикт
   отправителя, подтверждение вердикта.

## Тесты и замеры

```bash
cargo test --no-default-features --features nat-traversal
# стенд профилей канала (release, через прокси с потерями и задержкой):
cargo test --release --no-default-features --features nat-traversal --test e2e -- --ignored --nocapture bench
# только выбранные профили:
SHARP_BENCH="5%" cargo test --release --no-default-features --features nat-traversal --test e2e -- --ignored --nocapture bench
```

Юнит-тесты покрывают формат кадров (включая отказ на битых данных и
расширяемость), множества диапазонов (рандомизированно против битовой
карты), RTT/RTO/CUBIC/пейсер, запись/чтение файлов, хранилище состояний.
Сквозные тесты поднимают настоящих отправителя и получателя: файлы 0 байт …
3 МиБ побайтно совпадают; передача через прокси с 3–15 % потерь, дублями и
перестановкой завершается; сотни дыр после пакетного обрыва чинятся быстро;
получатель перезапускается посреди обрыва и передача возобновляется;
отправитель отменяется, исчезает без предупреждения или меняет файл;
параллельные передачи; отказ по политике; защита от перезаписи; простаивающие
и прерванные до данных сессии; потеря `FIN_DONE`.

Замеры этим кодом (release, одна машина, loopback; RTT и потери
эмулируются однопоточным прокси, который сам ограничивает скорость, поэтому
цифры — нижняя оценка и заметно колеблются от прогона к прогону):

| профиль | скорость | повторные передачи |
|---------|----------|--------------------|
| loopback без прокси, 512 МиБ на диск | 1,08–1,10 Гбит/с | 0 % |
| RTT 20 мс, без потерь, 64 МиБ | 335–505 Мбит/с | 0,1–3 % |
| RTT 100 мс, 0,1 % потерь, 32 МиБ | 135–143 Мбит/с | 1–7 % |
| RTT 20 мс, 1 % потерь, 32 МиБ | 190–270 Мбит/с | 1,1–1,3 % |
| RTT 20 мс, 5 % потерь, 16 МиБ | 90–190 Мбит/с | 5,2–13 % |
| RTT 20 мс, 1 % потерь, лимит 100 Мбит/с, 16 МиБ | 77 Мбит/с | 1,0–1,1 % |

Время включает рукопожатие, разгон, проверку хеша на обеих сторонах и
закрытие. Повторы сверх уровня случайных потерь на длинном RTT — это
«перелёт» медленного старта через мелкий буфер прокси, где задержка не
успевает вырасти (см. дорожную карту). На реальном канале скорость определяется его пропускной
способностью, RTT и потерями — управление перегрузкой подстраивается само.
Получатель сейчас упирается примерно в одно ядро CPU; для 10 GbE и выше
нужны пакетные системные вызовы (`sendmmsg`/`recvmmsg`, GSO/GRO).

## Дорожная карта

- Аутентифицированное рукопожатие и шифрование (X25519, Noise-подобное,
  AEAD) через бит возможностей; формат кадра уже резервирует 16-байтный
  слот тега.
- Манифест хешей 256 КиБ-блоков: проверка уже принятой части при
  возобновлении и локализация повреждений до финальной сверки.
- Пакетный ввод-вывод сокетов (`sendmmsg`/`recvmmsg`, UDP GSO/GRO) и
  многопоточный приём для многогигабитных каналов.
- Выход из медленного старта по измеренной скорости доставки (меньше
  «перелёта» на длинных каналах с мелкими буферами).
- Rendezvous/relay-сервис для случая, когда обе стороны за NAT.
- Передача каталогов и очередей файлов в одной сессии.
- Список разрешённых адресов отправителей для безголового получателя.
